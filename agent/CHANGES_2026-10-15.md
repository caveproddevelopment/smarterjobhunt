# Ingestion agent — 2026-10-15: descriptions out of the nightly scrape, returning jobs

Three changes:
1. The nightly scrape no longer fetches descriptions job by job, and keeps up to 5,000 jobs per company.
2. A new step, `run_description_backfill.py`, fetches descriptions only for jobs that aren't already in production.
3. A new step, `run_reactivate_returning_jobs.py`, sets a production job back to active when it shows up in the latest scrape again.

None of this has been run against real sites yet: this environment can't reach them. Everything passes
the automated tests (107), including tests against a real Postgres and a headless-browser test on a
local JavaScript job page.

## New nightly order

```
python run_ingestion_db_async.py              # 1. scrape -> jobs_staging (core info only)
python run_description_backfill.py            # 2. descriptions for jobs not in production
python run_reactivate_returning_jobs.py       # 3. returning jobs back to active
# 4. cleanup (delete staged rows with no description) and promote, as today
```

**Order matters.** Steps 2 and 3 must run before the cleanup in step 4:
- Step 2: if the cleanup runs first, the jobs it would have filled get deleted first.
- Step 3: a returning job's staged row usually has no description, because step 2 skips jobs already in
  production. If the cleanup deletes that row first, the proof that the job came back is gone.

To run steps 1–3 from one Railway cron command:
```
python run_ingestion_db_async.py && python run_description_backfill.py && python run_reactivate_returning_jobs.py
```

## First real run (do this once, in order)

1. `python run_description_backfill.py --dry-run` shows how many jobs it would fetch from each source
   and the busiest sites. It fetches and writes nothing.
2. `python run_description_backfill.py --limit 2000`, then look at the RESULT block (filled / failed
   by source, top failure reasons).
3. Then do the full catch-up: `python run_description_backfill.py` (20,000 jobs or 2 hours per run by default; run it again
   to continue).
4. `python run_reactivate_returning_jobs.py --dry-run` previews the count and 10 sample jobs. Then run it
   without `--dry-run`.

Check the big employers (JPMorgan, Macy's, Amgen) after the first scrape. Some Workday sites stop
serving results past a fixed offset on their side. If a company's list was cut short, the trace line
shows `truncated=...`.

## 1. Nightly scrape (`agent/ats_api.py`, `agent/async_career_scraper.py`)

- No per-job detail calls. `fetch_jobs(..., fetch_details=False)` is the default. Descriptions that come
  free in a platform's job list are still kept (Greenhouse, Lever, Ashby, Recruitee, and Oracle's short
  description).
- The careers-page scraper no longer opens each job's page (`SCRAPE_FETCHES_DESCRIPTIONS = False`).
  Descriptions found in the page's own JSON are still kept.
- `MAX_JOBS_PER_COMPANY`: 1,000 → 5,000.
- List paging stops after `LIST_BUDGET_SECONDS` (120s) and keeps what it has. 5,000 Workday jobs is 250
  requests, and the old 60s fetch cap would have thrown the whole list away. The per-fetch cap
  (`API_FETCH_TIMEOUT_SECONDS`) went from 60s to 150s.
- Workable: v3 search now follows `nextPage`, so it gets more than the first page.
- Fix: descriptions given as escaped HTML (Greenhouse's `content`, many JSON-LD blocks) were saved with
  literal `<p>` tags. They're cleaned now (`text_extract.html_to_text`).

## 2. `run_description_backfill.py` (+ `agent/description_fetch.py`)

**Which jobs:** rows in the latest batch of `jobs_staging` whose `raw_text` is empty or under 100
characters, that aren't rejected or already promoted, and that have **no row in `jobs`** with the same
`company_id` + `source_url`. Each unique link is fetched once, and every matching row is filled.

**Where descriptions come from:**
1. The platform API, worked out from the stored job link: Workday, SmartRecruiters, Oracle, Workable,
   Greenhouse and Lever.
2. Otherwise the job page over plain HTTP, using a JSON-LD `JobPosting` description if there is one,
   otherwise the main content block.
3. If that gives fewer than 100 characters (a JavaScript page), the page is rendered in headless
   Chromium (at most 4 pages at a time, `--render-pages`).

**Limits:** at most 2 requests at a time to any one site (`--per-host`). Platforms whose API is shared
by every company (SmartRecruiters, Greenhouse, Lever) count as one site. A run stops starting new
fetches at 20,000 links (`--limit`) or 2 hours (`--max-minutes`). Links are spread across sites so one
big employer doesn't hold up the rest.

**Failures:** recorded in a new table `description_fetch_failures`, which the script creates itself.
A link is skipped once it has failed 3 times (`--max-tries`, `--retry-dropped` to try again). Rate
limits (429), server errors and timeouts are recorded but don't count as a try.

**Only `raw_text` is written**, and only where it is empty or under 100 characters.

**Options:** `--batch-id <uuid>`, `--all-batches`, `--table <name>`, `--no-render`, `--dry-run`.

### Recovering the 98,625 rows backed up on 14 Oct (no re-scrape)

```
python run_description_backfill.py --table deleted_no_raw_text_jobs_staging_backup --all-batches --dry-run
python run_description_backfill.py --table deleted_no_raw_text_jobs_staging_backup --all-batches
```
Run it again until the dry run shows nothing left to fetch. Each run does up to 20,000 links. Rows
whose job is already in production are skipped.

The script only fills in the backup table. To put the filled rows back into staging for the normal
clean/promote:
```sql
BEGIN;
INSERT INTO jobs_staging (company_id, title, department, location, date_posted, source_url,
                          raw_text, scraped_at, batch_id, review_status)
SELECT b.company_id, b.title, b.department, b.location, b.date_posted, b.source_url,
       b.raw_text, b.scraped_at, b.batch_id, 'pending'
FROM deleted_no_raw_text_jobs_staging_backup b
WHERE char_length(btrim(coalesce(b.raw_text, ''))) >= 100
  AND NOT EXISTS (SELECT 1 FROM jobs_staging s
                  WHERE s.company_id = b.company_id AND s.source_url = b.source_url
                    AND s.batch_id = b.batch_id);
-- check the count, then COMMIT (or ROLLBACK)
```
Then run clean/promote for those batch ids as usual.

## 3. `run_reactivate_returning_jobs.py`

**What it does:** sets `is_active = TRUE` and `scraped_at` to the time the job was seen. It does this
for inactive production jobs whose `company_id` + `source_url` appear in the latest scrape batch (any
review status), and only when the production row already has a description (100+ characters). It
changes nothing else, so existing production rows are never overwritten.

**How it runs:** it previews first, then applies in one transaction, and prints
`Reactivated N returning jobs`. Use `--dry-run` for the preview alone, or `--batch-id` to pick a batch.
The same steps as SQL, for Claude in Chrome, are in `REACTIVATE_RETURNING_JOBS_for_Claude_in_Chrome.md`.
