# Ingestion agent — 2026-11-13: descriptions for `#job-` links (Gem, UKG, Dover)

Fixes the ~1,000 scraped jobs (the last two runs) that could never get a description because their
stored link is `<listing page>#job-<id>` and the backfill skipped every such link. Plan: the
"Fix: Gem & Dover #job- descriptions (JobBeggar backfill)" doc, 12 Nov.

Only the description backfill changes. The scraper, `job_json.py`, promote, reactivation and the
`jobs` schema are untouched, and **`source_url` is never rewritten** (it is half of the
`(company_id, source_url)` dedup key; rewriting it would make the next scrape see every one of these
jobs as new).

## What changed

1. **Backfill lets handled `#job-` links through** (`run_description_backfill.build_filters`).
   The blanket `NOT LIKE '%#job-%'` is now: not `#job-`, **or** the host matches
   `ats_api.ANCHOR_HOST_LIKE`. That host list is built from `ats_api._ANCHOR_PATTERNS`, so a host
   is only let through once it has a handler, and the two can't drift. `#job-` links on any other
   host stay skipped, exactly as before.
2. **`#job-` links never fall through to the page fetch** (`description_fetch.fetch_description`).
   The page is only the listing page. With no handler the result is `error="no_handler"`; a handler
   that finds no job (closed) gives `too_short`, the normal closed-job outcome.
3. **`_ANCHOR_PATTERNS`** in `agent/ats_api.py` (regex, source, handler, host patterns), checked by
   `detail_source_for_url()` and `detail_for_url()` after `_DETAIL_PATTERNS`.
4. **Gem handler** `detail_gem(board, job_id)`: keyless Job Board API
   `GET https://api.gem.com/job_board/v0/{board}/job_posts/`, one request per board per run (cached
   30 min, errors not cached), all Gem boards share one per-host limit (`api.gem.com`). The post is
   matched on its ID as stored (`T2F0c0pv…==`), base64-decoded (`OatsJobPost:7480329`) or numeric;
   description from `content` (then `description`, `content_html`…).
5. **UKG Pro Recruiting (UltiPro) handler** `detail_ukg(host, tenant, board, opportunity_id)`:
   fetches `https://{host}/{TENANT}/JobBoard/{board}/OpportunityDetail?opportunityId={id}` (built
   for fetching only) and reads the JSON the page passes to
   `US.Opportunity.CandidateOpportunityDetail({...})`. Hosts: `recruiting.ultipro.com`,
   `recruiting2.ultipro.com`, `*.rec.pro.ukg.net`. **1 request at a time per UKG host**
   (`ats_api.PER_HOST_LIMIT`), whatever `--per-host` is.
6. **Dover handler** `detail_dover(job_id)`: keyless
   `GET https://jobs.dover.com/api/v1/jobs/{uuid}/get_job_description` (the call Dover's own job page
   makes). The plan expected a page render; it isn't needed.
7. Tests: 33 new in `tests/test_descriptions.py`, plus `test_gem_anchor_links_selected_and_source_url_kept`
   in `tests/test_backfill_db.py` (Gem/UKG/Dover links fetched, unknown-host `#job-` still skipped,
   `source_url` unchanged). Full suite **182 passed, 0 skipped**, including the Postgres tests
   (run against a local Postgres 16).

## How the platforms behave (checked live in Chrome, 13 Nov)

- **UKG** (recruiting.ultipro.com/YAS1000YAAMI): the board's list
  (`JobBoardView/LoadSearchResults`) gives each job an `Id` GUID and no link, which is what
  `job_json` stores after `#job-`. The detail page's **plain HTML** (no JavaScript) carries the job
  object with `Description` (HTML), `Id` and `OpportunityIsClosed`. An unknown/closed ID returns
  HTTP 200 without the object → `""`.
- **Dover** (jobs.dover.com/dover): the list
  (`/api/v1/job-groups/{client id}/job-groups`) gives each job an `id` UUID and no link. The job
  page HTML is a 4 KB JavaScript shell; the description comes from `get_job_description`, no login.
  `user_provided_description` (HTML) is what the page shows. `user_facing_description` (markdown)
  **was stale** on the job checked (it described a different role), so it is only a fallback.
  `use_dover_jd=true` → the page shows `generated_description` sections instead. Unknown job → 404,
  unpublished → `is_published=false`; both → `""`.
- **Gem: not verified live.** The help-center page blocks fetching and the API isn't reachable from
  here. Field names (`id`, `content`) are the likely ones and the matching is deliberately broad.
  **Check before the real run:** open
  `https://api.gem.com/job_board/v0/cartwheel-1/job_posts/` and confirm the ID field matches our
  `#job-` value and the description field is `content`.

## Rollout (from the plan)

1. `python -m pytest tests -q` (with `SJH_TEST_DATABASE_URL` set to run the Postgres tests too).
2. Dry run, Funded Startups staging:
   `python run_description_backfill.py --all-batches --dry-run`
   "Planned fetches by source" should now show about **186 `gem`** and **11 `dover`**.
3. Real run: same command without `--dry-run`, then promote as usual. The RESULT block should list
   `gem` and `dover` under "Filled by source".
4. Mid-Sized backlog (UKG, 764 rows):
   `python run_description_backfill.py --table staging_archive_20261112 --all-batches`
   These are in an archive table, so filling them publishes nothing. **Check with Monte before moving
   any into `jobs`.**
5. Deploy by commit to `main`. The Scraping-Agent start command is currently the backfill; Monte
   controls when it changes.

Done when: ≥90% of the 186 Gem rows filled; ≥80% of the 764 UKG archive rows filled (or a note why
not); tests pass and RESULT shows `gem` and `ukg`; no `source_url` changed (spot-check 10 filled rows).

Still out of scope: the ~550 Mid-Sized rows on single-company sites, the 18 Greenhouse
`ConnectionError` rows, promote/reactivation/schema, promoting the archive rows.
