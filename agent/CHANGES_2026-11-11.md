# Ingestion agent — 2026-11-11: Phenom handler, careers-URL fix

Branch `phenom-handler`. Nothing here touches the database code or the nightly order. Don't merge to
`main` until the dry runs below have been run from a machine that can reach the sites: a push to `main`
redeploys Scraping-Agent and starts a full scrape.

## What changed

1. **Phenom API handler** (`agent/ats_api.py`: `_fetch_phenom`, `detail_phenom`). Phenom career
   sites (Adobe, Advance Auto Parts, Chewy, Acadia, TJX, United, Humana, PNC, Ecolab ...) are now
   read through the site's own `/widgets` JSON API instead of the browser scraper.
2. **Phenom detection** (`agent/platforms.py`: `parse_phenom_config`, `phenom_token`;
   `agent/ats_detector.py`). Phenom sites run on the company's own domain, so they're recognised by
   the `phApp = phApp || {...}` settings block every Phenom page carries. Token:
   `"<host>|<base path>"`, e.g. `careers.adobe.com|us/en`, `jobs.tjx.com|global/en`.
3. **Careers-URL fix** (`ats_detector._extract_ats_from_html`, `platforms.is_static_asset_url`).
   The detector took the first link to a hiring-platform host as the careers URL, even when it was a
   script or stylesheet. Adobe got `cdn.phenompeople.com/.../globalstyles.css`, and Exxon Mobil got
   `performancemanager4.successfactors.com/.../jquery.js`. A link to a platform's file (js, css,
   fonts, images, or a `cdn.`/`rmkcdn.`/`static.` host) now means *this page is built on that
   platform*, so the page itself is returned as the careers URL.
4. **Careers subdomain scan** (`ats_detector.detect_ats`). `adobe.com/careers` is a marketing page
   (`adobe.com/careers.html`) that only links to careers.adobe.com, so detection stopped there with
   `ats=unknown`. When the chosen careers page shows no platform, the `careers.`/`jobs.` subdomains
   that were already confirmed as working pages are scanned too (`detected_via=...+subdomain_scan`).
5. `tools/phenom_dry_run.py` and `tests/test_phenom.py` (32 tests). Full suite: 134 passed,
   11 skipped (the Postgres ones).

## How the Phenom API behaves (checked live in Chrome, 11 Nov)

| Site | Path | Jobs | Notes |
|---|---|---|---|
| careers.adobe.com | us/en | 268 | sends `jobUrl` |
| jobs.advanceautoparts.com | us/en | 16,284 | sends `jobUrl`; over the 9,999 window |
| careers.chewy.com | us/en | 239 | `jobs.chewy.com` doesn't resolve |
| www.acadiacareers.com | us/en | 1,484 | `acadiahealthcare.com/about/careers/` redirects here |
| jobs.tjx.com | global/en | 10,049 | over the 9,999 window |
| careers.united.com | us/en | 130 | |
| careers.humana.com | us/en | 2,147 | remote jobs have no city/state; shown as "Remote" |
| careers.pnc.com | global/en | 1,995 | Apply buttons go to Workday; Phenom is still the source |
| jobs.ecolab.com | global/en | 1,000 | facet counts agree, so it's a real count, not a cap |

- `POST <host>/widgets` with `ddoKey: "refineSearch"`. Needs no cookies or CSRF token.
- **Page size is capped at 500.** Asking for 1,000 returns 500.
- **Paging stops at 9,999.** If `from + size` is over 9,999, the call returns 0 jobs and `totalHits` 0.
- **Paging isn't stable.** Result order shifts between calls. Paging Advance Auto's 1,925 Florida jobs
  100 at a time returned only 1,760–1,865 different jobs. Sorting by relevance, date, title, `jobId`
  or `jobSeqNo` didn't fix it. A search that fits in one call loses nothing.
- So the handler asks for 500 at a time and, when a search has more, splits it by a facet (state,
  country, job type, category, city: the one whose largest part is smallest), recursively, until
  each part fits in one call. A part that can't be split is paged up to 3 times and the passes merged.
- Descriptions: every job has `descriptionTeaser` (200–330 chars), so the nightly snippet passes the
  100-character bar without detail calls. `detail_phenom` (`ddoKey: "jobDetail"`) returns the full text
  (3,000–33,000 chars). It isn't in `_DETAIL_PATTERNS`: Phenom job links live on company domains, so
  a URL pattern can't tell them from other sites, and an API failure there has no page fallback.
- Job links: `jobUrl` when sent, else `<baseUrl>job/<jobId>/<title, each run of non-alphanumerics
  turned into one ->`, which is exactly what the sites' own pages link to. For example,
  "Functional Developer II – Oracle ERP Finance" →
  `careers.chewy.com/us/en/job/R30723/Functional-Developer-II-Oracle-ERP-Finance`.

## Page size: 100 vs 500 (Advance Auto, all 16,284 jobs)

| Method | Page size | Jobs found | Calls | Time |
|---|---|---|---|---|
| plain paging, split by state | 100 | 15,913 | 195 | 74s |
| plain paging, split by state | 500 | 16,231 | 69 | 40s |
| this handler | 500 | **16,284** | 139 | 72s |
| this handler | 100 | (not finished after 8 min) | | |

`PHENOM_PAGE_SIZE = 500`. At 100, every search over 100 jobs has to be split or paged, which is far
slower and loses more to the unstable order.

## Job cap for Phenom boards (follow-up, 11 Nov)

`MAX_JOBS_PER_COMPANY` (5,000) used to cut Advance Auto from 16,284 to 5,000 and TJX from 10,049 to 5,000.
Phenom boards now have their own cap, `PHENOM_MAX_JOBS = 25000` (`ats_api._job_cap`). Other platforms
stay at 5,000. The time limits are unchanged:

- `LIST_BUDGET_SECONDS` (120s) still stops paging and keeps what was fetched. In Chrome, all of Advance
  Auto took 72s and TJX 64s. If the server is slower, the run keeps a partial list and the trace shows
  `truncated=list paging stopped after 120s`.
- `API_FETCH_TIMEOUT_SECONDS` (150s, orchestrator) is still above the budget, so a slow board never
  loses everything.
- After the first nightly run, check Advance Auto and TJX in the trace: about 16,300 and 10,000 jobs, and no
  `truncated`.

Other notes:
- `jobs.chewy.com` (from the task list) doesn't resolve; Chewy's site is `careers.chewy.com`.
